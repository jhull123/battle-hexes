# Introduction

Deliver one experimental, human-playable 9×9 PPO opponent using a **trained, saved, reloaded** multi-unit policy. This increment proves the live core/API/UI path; it does not establish playing strength or produce a Crossroads policy.

## 1. Purpose & Scope

For implementers and reviewers of [schedule 2, increment 07](playable-player-schedule.md), extend the [06 prototype](06-multi-unit-design.md) with bounded masked training, a validated frozen artifact, and a backend-connected human game. Support exactly the fixed two-versus-two setup, PPO as the **first** side (`Learner`), and Human, Random or Q-Learning as the second (`Opponent`). The human-versus-PPO durable-browser demonstration remains the acceptance gate. Keep existing 5×5 training/inference and ordinary batch-player games working. Crossroads, arbitrary rosters/boards, self-play, checkpoint selection campaigns, and a strength threshold are out of scope.

## 2. Definitions

- **PPO:** Proximal Policy Optimization, implemented by SB3-Contrib `MaskablePPO` with `MultiInputPolicy`.
- **Slot/order:** A persistent unit ID and its one destination choice per friendly movement phase. One PPO request issues at most one order.
- **Cycle:** One PPO turn followed by one second-side turn, unless core completes earlier. Core turn number identifies the current cycle.
- **Mask:** A 162-element boolean vector; `True` means that the slot/destination is currently legal under core movement rules.
- **Checkpoint identity:** A manifest-listed artifact name plus its SHA-256 digest and policy contract, bound to a game at creation.
- **Cutoff:** An external training/evaluation stopping bound while core remains `in_progress`; not a game result.
- **Completed result:** Core `GameStatus.state == "completed"`, by elimination or the declared turn limit. With no objectives to score, a game that reaches the turn limit without elimination ends in a 0–0 draw; wins and losses require elimination.

## 3. Requirements, Constraints & Guidelines

- **REQ-001 — Playable contract:** Use `battle-hexes-9x9-2slot-unit-destination-live-turnlimit10-v3` for scenario `ppo_9x9_experimental`, version `2`. Keep 06's `...live-v1` prototype unchanged and reject both its checkpoints and the superseded 50-turn v2 checkpoints for playable games. Set a **10-cycle core turn limit** so a game can finish within the policy's horizon; neutral open terrain must have movement cost 1, defensive-fire modifier 1 and combat odds shift 0. Train, evaluate and serve **v3** on the same core-loaded scenario, including its turn-limit scoring. Do not relabel earlier weights or reinterpret their `remaining_cycles` input. Version 1 saved games are incompatible with the changed rules.
- **REQ-002 — Policy input and turns:** Retain 06's four stable slots, Dict observation shapes/dtypes, `Discrete(162)` mapping (`slot * 81 + row * 9 + column`), core-derived mask and path validation, hold action, live defensive fire, post-order retreat feedback, and single combat phase per side. For v3, `remaining_cycles` is `[11 - game.turn_number]` (10 at reset, 1 on turn 10); never derive it from a smaller smoke/evaluation cutoff. An eliminated/ordered slot cannot be selected again. Once no living PPO slot is pending, use core's movement-phase closure, one combat resolution if applicable, and end-turn transition; stop at core completion, including completion during movement. The second side uses its existing human or CPU movement/combat workflow and returns to PPO only after core ends that turn. Both sides use the same scenario rules and core resolution; neither route nor schema computes victory.
- **REQ-003 — Training:** Provide a bounded CPU masked-PPO command with seed, positive requested timesteps, rollout size (>1), batch size (>1 and no greater than rollout size), and a new run directory. A repository training launcher targets one Git-tracked model under `battle_agent_rl/archive/ppo/` per architecture (`x86_64` or `arm64`), explicitly removing only that target's previous generated files before calling the bounded trainer. It defaults to the host architecture; on x86, selecting ARM64 trains with the pinned ARM64 runtime under Docker/QEMU, never during deployment. Use native current-state masks during **both** rollout and deterministic prediction. Preserve 06's sorted-joint-index seeded random opponent for training/evaluation only; the selected second-side controller replaces it in playable games. Record actual timesteps, completed optimizer updates, outcomes and cutoff counts separately, and evidence that at least one tensor changes. Keep training dependencies out of core and the lightweight 06 inspector.
- **REQ-004 — Artifact:** Save a model after a completed update, with a versioned JSON manifest recording scenario ID/version or immutable gameplay fingerprint, v3 contract, 10-turn horizon, action/observation spaces, roster/seat, training seed/configuration and actual timesteps, CPU/software versions, relative model path and SHA-256 digest. Exclude scenario name, faction colors and sound filenames from the gameplay fingerprint; they do not affect policy input or core rules. The bounded trainer itself does not overwrite an existing run; only the explicit architecture training launcher replaces its selected, tracked model. Paths do not include policy-version suffixes, though the manifest retains its compatibility contract. Load on CPU in a fresh process; verify the manifest, file digest, versions, spaces, scenario/rules and slot mapping **before** prediction. Reject unknown paths, v1/v2/5×5 archives, corrupt or incompatible models, and missing serving artifacts with clear errors; never silently use initialized/random weights. The serving artifact is an administrator-configured, manifest-listed checkpoint, not a client-provided filesystem path; fail unavailable at selection/creation rather than mid-turn. Replacing a committed model expires saved games bound to its former digest; GET and commands fail with an explicit checkpoint-unavailable error in the server log and browser rather than substituting the new model.
- **REQ-005 — Frozen live inference:** Encode observations/masks and convert actions to core plans using shared v3 training/inference code; choose once with `deterministic=True` and the current mask. Validate action legality and path before applying one plan through core; never substitute hold after a bad prediction. Predict again only after that move and its fire/retreat have been resolved and persisted. Do not train, assign rewards or mutate model weights in callbacks or HTTP commands. Refuse a wrong side, phase, scenario, roster, horizon, checkpoint or empty active mask rather than running a batch `Player.movement()` that cannot observe fire between orders.
- **REQ-006 — Durable turns:** Persist the checkpoint identity, PPO pending slot IDs and shared game RNG continuation with the authoritative game state. Prune a pending slot if its unit dies; never restore it by recomputing from remaining movement points. Validate these fields against the scenario, current player/phase, living units and the **game-bound** manifest entry on hydration; if its artifact is no longer available, fail rather than substituting the server's new default. Do not serialize a model, executable object or pickle into game state; use validated JSON data for RNG continuation. Every successful PPO order atomically commits its movement, fire, pending changes and RNG state with the next game version under the existing expected-version/idempotency protocol. The final PPO order also finishes that side's movement, resolves its one combat phase and advances through core when active. Existing human commands for this scenario must use the same persisted RNG continuation for fire and combat; retries/reloads must not resample rolls or issue another order. On completion persist core's terminal phase/status consistently with the existing codec. Make the persisted extension optional for older/non-PPO snapshots, with an explicit state-schema migration if required; do not alter non-PPO turn behavior.
- **REQ-007 — API boundary:** Advertise a separately named `ppo-9x9-experimental` player type, restricted to the first seat on `ppo_9x9_experimental`, with Human, Random or Q-Learning in the second seat. Reject unsupported combinations at creation with a client error. Add one PPO-only atomic order command (section 4); do not expose client-selected PPO actions, generic `/movement` batching, or manual end-movement/combat/turn commands on the PPO side. Allow `/movement` only on a second-seat CPU movement turn; preserve `/move` only for a human second seat and `/end-movement`, `/combat` and `/end-turn` for either second-seat type with authoritative ownership/phase checks. Persist CPU-side fire/combat RNG with the same game-bound continuation; retries/reloads must not resample rolls. Keep routes thin, core rules in core, and API schemas limited to validation/serialization of already-computed results.
- **REQ-008 — Human-visible result:** Offer Elimination Demo 3 and the **Trained 9×9 PPO** choice only in the supported seats. Provide both factions with Elimination Demo 1's defensive-fire sound mappings, visible in the API game payload so the existing frontend sound player can play effect/no-effect audio when events occur. The backend-connected UI issues and animates each PPO order separately, shows defensive fire/retreat before requesting the next order, shows combat and handoff once per side, and resumes from `GET /games/{id}` after reload using authoritative pending/phase and checkpoint identity. Start a second-seat CPU turn after PPO hands off and return to PPO after its turn; render core-completed win/loss/draw and reason using existing game-over behavior. Never display a training/evaluation cutoff as a completed human game. Preserve ordinary CPU/batch player UI behavior.
- **CON-001:** The playable game has no external 10-cycle cutoff: on the last completed second-side turn, core's 10-turn rule decides the result. Because this scenario has no objectives and awards no score, a non-elimination turn-limit result is always a 0–0 draw. If an evaluation intentionally stops earlier, report `cutoff` with core still `in_progress`; completion on the bound takes precedence.
- **CON-002:** Split scenario/policy conversion, trainer, artifact validation, live turn orchestration, API command adaptation, persistence and UI rendering by responsibility. Reuse the live resolution sequence and current-state encoder rather than duplicating training/inference implementations. If implementation must depart from this numbered contract, ask the user before changing it.

## 4. Interfaces & Data Contracts

### Fixed scenario and policy

Scenario JSON is registered under `battle_hexes_core/src/battle_hexes_core/scenarios/`: 9×9; 10-turn core limit; no objectives, roads, reinforcements or stacking cap; default fire base `0.25`, minimum `0`, maximum `1`; two infantry per side, attack/defense/move `2/2/2`, fire modifier `1`. Player order and unit insertion order: `Learner`/`learner-0` at `(3,2)`, `learner-1` at `(5,2)`; `Opponent`/`opponent-0` at `(3,6)`, `opponent-1` at `(5,6)`. A neutral visual terrain must not change these rules. Define the core-loader scenario once; training must not maintain a conflicting hand-built scenario.

The 06 observation fields remain `positions` (`int8[4,81]`), `present`, `alive`, `movement_remaining`, `defensive_fire_ready`, `fire_eligible_last_turn`, `forced_retreat`, `fire_spent` (each `int8[4]`), `pending` (`int8[2]`), and `remaining_cycles` (`int32[1]`, range 0–10). The separate mask is `bool[162]`; missing/dead slots retain the 06 padding/identity semantics. The first holds are actions `29` and `128`. A last-unit death completes via core even if the other slot was pending.

### Training and evaluation entry points

Use `./battle_agent_rl/train-ppo.sh` for a fresh host-architecture model or `./battle_agent_rl/train-ppo.sh arm64` to train ARM64 locally on x86. Both invoke the bounded `multi_unit_train` entry point with a new run directory after clearing their selected tracked output. Keep its explicit seed, requested timesteps, rollout and batch arguments available for independent experiments. `python -m battle_agent_rl.ppo.multi_unit_evaluate --run-dir battle_agent_rl/archive/ppo/x86_64 --seeds 1000:1020` replays the native x86 checkpoint; use a matching ARM64 runtime to evaluate the ARM64 checkpoint. Predeclare and record ordered evaluation seeds `1000..1019` for the demonstration; reject overlap with recorded training episode seeds. Evaluation reloads the saved artifact, runs one game per seed with core completion or a declared external cycle cap, and records `{gameSeed, outcome: win|loss|draw|cutoff, learnerDecisions, coreStatus}`. Report four counts over all seeds; no win-rate gate or held-out strength claim is required. For an early cap, still supply the true 10-turn `remaining_cycles` to the model. Evaluation reports are not part of the committed checkpoint directories.

### API and persisted state

- `POST /games` accepts `{ "scenarioId": "ppo_9x9_experimental", "playerTypes": ["ppo-9x9-experimental", "human"] }`, with `"random"` or `"q-learning"` also allowed in the second seat, only when the configured validated artifact is available. The v3 checkpoint retains the established manifest seat metadata; the second player's runtime controller does not change the policy inputs or rules.
- `POST /games/{game_id}/ppo/order` has no client-selected action and requires the existing `Idempotency-Key` and `Expected-Game-Version` headers. It commits **at most one** PPO order; response includes the resulting `gameVersion`, `game` projection, one `plan` (`unitId` and path), this command's `defensiveFireEvents`, this command's combat events if it closed movement, and authoritative `ppoTurn` (`pendingUnitIds`, `checkpointDigest`, `contract`). Use HTTP API camelCase. An early core completion may omit further combat; `pendingUnitIds` is empty when no next PPO decision exists. An incompatible state, non-PPO phase, stale expected version or missing game-bound artifact fails without committing state; an exact retry returns the original receipt.
- `GET /games/{game_id}` includes the optional `ppoTurn` metadata whenever this game uses PPO (pending list empty off the PPO movement phase), and the existing game status/phase. The authoritative persisted extension stores validated checkpoint identity, two-slot pending state and RNG continuation; it is preserved across process restart and optimistic-concurrency retries. No existing client must require `ppoTurn` on other games.

## 5. Acceptance Criteria

- **AC-001:** Given the v3 contract on the version-2 scenario and bounded seed-0 run, when training ends, then masked rollout actions are legal, at least one optimizer update changes parameters, and a versioned manifest and model exist. Given its reloaded checkpoint, deterministic masked actions match pre-save actions on matching live decision states without weight changes.
- **AC-002:** Given v1/5×5, wrong scenario/side/turn limit, missing/damaged artifact or changed software/spaces, when a game is created or a model loaded, then the attempt is rejected before a PPO order; existing 06 inspection and 5×5 tests still pass.
- **AC-003:** Given two PPO units pending, when the first order triggers defensive fire and retreat/removal, then the next response/observation/mask reflect the resolved state, the first unit is not offered again, and combat has not run. On the final order, combat runs at most once and core hands off to the second side unless completed.
- **AC-004:** Given a pending second order, when the browser or server restarts, then GET and the next successful command use the same checkpoint digest, pending slot, movement/fire state and RNG continuation. Replaying a key produces the same response without another order; stale versions, wrong phase and incompatible snapshots fail without mutation.
- **AC-005:** Given a human acting second, when both sides complete turns, then existing human commands still work and PPO decisions are one-at-a-time. Elimination produces a core-completed winner; reaching the end of core turn 10 without elimination produces a 0–0 draw. The backend and UI show the same completed result and reason. An evaluation cutoff with core `in_progress` is not shown as a human-game result.
- **AC-006:** Given declared seeds `1000..1019`, when evaluating the saved model, then per-seed records and win/loss/draw/cutoff totals reconcile and rerunning with the same artifact, seed/RNG protocol and runtime reproduces records. The report makes no strength claim from the smoke run.
- **AC-007:** Given a non-PPO game, when its existing API and UI movement/combat flow runs, then the batch-player contract, persistence and responses remain usable. Given a PPO game with a Random or Q-Learning second seat, when the PPO turn ends or the game reloads on the CPU turn, then the second player moves, resolves its phases through core, returns control to PPO, and preserves its game-bound RNG and command receipts; batch movement remains forbidden on the PPO turn.

## 6. Test Automation Strategy

- **Unit (`pytest`, `battle_agent_rl/tests/ppo`):** Short real masked training; changed weights, legal mask on rollout/prediction, fresh-process reload, digest/version/space/scenario rejection, stable slots and post-fire parity. Compare matched core decision states from trainer and live service; never infer identical trajectories from seed alone when the human differs from the random training opponent.
- **API/persistence (`pytest`):** Real core command paths, supported/unsupported seat creation, two-order mid-turn hydration (in-memory and configured durable repository tests), optimistic concurrency and receipt replay, persisted RNG continuity, terminal codec validation, fire/combat event visibility, and regression coverage for random/Q-learning batch players. Test outcomes/phase transitions, not exact log strings.
- **Web (existing JS tests):** Supported-seat picker, per-order animation and event display, reload/resume with pending order, terminal display and unchanged ordinary CPU play. Run `npm run test-and-build` for web changes.
- **Backend-connected acceptance:** Run the actual API with a configured trained artifact and persistent repository; record a reproducible human-versus-PPO playthrough including live fire/retreat, mid-turn reload and a core-completed result. A CLI trace, mock service, initialized model or cutoff does **not** pass this gate. Run `./server-side-checks.sh`; keep the smoke run bounded and record separate evaluation artifacts, not a skill-threshold CI test.

## 7. Rationale & Context

The 06 policy sees remaining *cycles* and has no core time limit. A human game allowed to continue past its 10-cycle horizon would change the input semantics or leave the observation space. The version-2 scenario with a matching 10-turn core limit and v3 checkpoint replaces the superseded 50-turn playable contract; do not silently reuse v2 weights. Per-order API commands are necessary because `Player.movement()` chooses an entire batch before seeing defensive fire; versioned receipts and persisted pending/RNG state allow the UI to reload between choices. A fixed smoke run tests connectivity and artifact integrity, not generalization; Crossroads requires its own contract and training in 08–12.

## 8. Dependencies & External Integrations

- **EXT-001:** Core scenario loader, movement plans/reachability, defensive fire, combat, phase transitions and game-status evaluation; core remains independent of PPO libraries.
- **PLT-001:** Existing CPU Python/Gymnasium/NumPy/PyTorch/SB3-Contrib stack for training and prediction, plus existing FastAPI and p5.js application contracts.
- **DAT-001:** 06 slot/action/observation design and 04 artifact-validation conventions; a newly trained **v3** artifact is required for serving.
- **INF-001:** Existing API game repository, codec, expected-version and idempotency receipt mechanism, and a deployment-accessible configured checkpoint; browser never reads model files.

## 9. Examples & Edge Cases

- At turn 1 with both PPO slots pending, `remaining_cycles=[10]`; ordering slot 1 to hold at `(5,2)` uses `128`, leaves slot 0 pending, and does **not** start combat. At the next prediction the mask contains only slot 0's block, based on the post-order board/fire state.
- If defensive fire eliminates the first mover, its order remains spent. If it eliminates the last opposing unit, core completes immediately: do not predict, execute combat or hand off afterward.
- A game still active after PPO's turn-10 orders remains active until the second side finishes, unless core completes sooner. If neither side is eliminated, core completes that turn as a 0–0 draw. A smoke evaluation deliberately stopped after turn 3 instead records `cutoff`, core `in_progress`.
- After a committed first order, retrying its idempotency key returns that same result; a **new** key with the old expected version conflicts. A fresh request after reload can order only a still-pending unit and must use the game-bound digest, not the server's newly configured default artifact.
